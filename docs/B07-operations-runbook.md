# B07 incident, restore and migration runbook

This is an operator-review proposal, not authorization to act on a live environment. [Drill plan](B07-drill-matrix.md), [executed results and limits](B07-verification.md), [B06 invariants](B06-invariants.md), [B04 sessions](refresh-family-policy.md). Roles below are proposed functions, not named people or accepted on-call assignments. Thresholds need owner confirmation; local timings are not SLOs.

## Before any operational action

Confirm exact environment/namespace, connection target without printing credentials, owner approval, current release and manifest. Verify resource ID/name/label/binding, backup scope and active writers. A historical document, screenshot or cleaned=true flag cannot authorize a container command. Stop if ownership is uncertain or money/stock/receipt/permission invariants fail. Never bulk kill processes, prune/flush shared Redis, delete commerce tombstones, drop indexes to bypass errors, or mark payments/refunds complete without evidence.

## MongoDB readiness/auth failure

Signal: live endpoint responds but `/api/home/health` fails, HTTP auth/read/create error or bounded timeout, server-selection/network errors. Impact: DB-backed authorization must not succeed through fallback; existing access JWT is insufficient without current DB checks. Proposed role: backend on-call with database operator.

Verify deployment target, replica topology/PRIMARY, connection pool and index readiness. Keep same request key/body across ambiguous failures. After DB recovers, first lookup the attempt; terminate only under the published recovery contract. created means recover its result, invalidated/canRestart means an independent new purchase is allowed after review; unknown is inconclusive. Check checkout/order/stock/coupon/receipt/allocation/refund before reopening traffic. Do not infer no commit from an HTTP timeout or start a second purchase automatically.

B07 one-node pause is an outage, not HA failover. The fixture uses selection=2s/socket=3s to bound this test; runtime configuration was not changed to achieve it. Readiness ping has its own existing 2s bound. HTTP 500 as well as 503 was observed during Mongo loss; no false 2xx. Full multi-node partition/failover and a post-commit lost Mongo ACK need separate controlled topology drills.

## Mongo silent transaction drain (B-A1-AV01)

Owner Q accepted B-A1-AV01 as an open P2 on 22/10/2026, subject to [scope and expiry](BE-open-issues.md). This procedure is documented mitigation, not an executed deployment drill or permission to operate a live target. Edge deadlines and deployed readiness/p99 alerts remain unverified. The driver retry window around 120s is not a hard timeout on silent TCP I/O; an edge timeout does not cancel or prove rollback of a Mongo transaction.

1. Confirm the approved environment, exact instance IDs, release and incident scope. Hold new purchase admission at the approved edge/traffic control before draining affected instances; include product/subscription create and prepare. Preserve the original request references and bodies for recovery without publishing credentials or personal data. Do not acknowledge a webhook as durably accepted unless the existing handler actually recorded it; preserve the provider's documented retry path.
2. Observe in-flight requests, DB PRIMARY/topology, per-instance readiness, latency/p99 and dependency error logs using requestId. Do not treat a successful ping as proof that all transaction/commit waits have ended. Keep unresolved requests as unknown; do not create replacement keys, cancel obligations or clear queues to make the drain appear complete.
3. If an instance restart is required under the approved incident plan, use the existing graceful SIGTERM path on that exact instance. Source server.js marks stopping, stops workers and closes connections, with a 10s forced-exit timer. That timer is not a transaction deadline or proof of rollback. Do not blindly wait 120s then declare failure; record any unfinished commit as unknown. Do not kill shared Mongo/Redis processes or modify ledger/paid flags, indexes, leases or tombstones.
4. After Mongo recovers, check readiness on every serving instance and the intended topology/indexes. Resolve/replay each ambiguous operation with the same authenticated user/kind/key/body under the attempt contract. Verify one obligation, original stock/coupon snapshots, receipt/allocation/refund conservation and worker/outbox recovery; use existing command idempotency for reconciliation/refund work. Stop and escalate any duplicate/missing obligation or invariant failure before reopening admission.
5. Restore only traffic already authorized for that environment, with observation and a reviewed workload. This acceptance does not permit real-user staging or opening sales while B-A1-AV01 remains open. Close it through A2 or another evidenced owner decision before either gate; review again after DR03/DR05 and the load phase. Record the actual edge timeout and demonstrated alert delivery in the risk record when they are verified.

## Redis failure, sessions and streams

Signal: readiness 503, shared limiter errors/deadlines, streams close, pending security events. Proposed role: backend/platform operator. Verify Redis readiness and both publisher/subscriber health; check namespace and exact owned target before recovery. Keep HTTP writes fail-closed. DB revocation is authoritative: a recovered Redis or restarted process must not reactivate a revoked family. Other families remain DB-valid; outage can close their SSE transport too.

Restore service, observe security backlog publication and readiness on every instance, then verify revoked access is still rejected and unaffected family access is preserved. Do not clear sessions/tombstones or Redis wholesale to hide backlog. Published security notifications are at-least-once; consumers must tolerate repeats. Existing B04 heartbeat checks DB approximately every 20s plus DB latency; this is not a hard deadline under stalled DB I/O.

## Worker backlog and retry

- **Expiry:** no cross-process lease. Due checkout scan, then common checkout revision/transaction and state predicates fence cancellation/refund/coupon writes. Errors retry on later minute ticks. B07 injects an Order save failure after its transactional write and proves rollback, then restarts and runs competing ticks. Safe action: fix DB cause and rerun due work; do not raw-delete orders or refund receipts.
- **Delivery:** no distributed scan lease. Unique subscription/sequence upsert dedups due fulfillment creation. A failed acknowledgement after upsert can leave the work item already present. B07 restarts and retries without creating another item. This scheduler does not dispatch stock or deliver parcels automatically; paid/active eligibility is required. Actual dispatch/delivery uses subscription revision, pinned BoxVersion and transaction. Proposed role: backend plus fulfillment operations; do not decrement remaining deliveries by raw update.
- **Payment reconciliation:** due unallocated events, max50/tick, no scan lease. Shared checkout revision plus unique allocation/event and audit command keys fence concurrent workers. Failure increments attempts and schedules nextAttempt about60s later. Receipt admission is durable before settlement acknowledgement. Correct source/config/stock issue, inspect receipt and ledger, let worker retry under the same receipt identity. Never manufacture allocations or change paid flags to clear a queue. B07 fault rolls back allocation while retaining receipt, then two real drains settle once.
- **Notification outbox:** atomic claim pending/due/lease expired, 60s lease, retry backoff `min(1h,1s×2^min(attempts,10))`. It has no leaseId fencing on final marker, so transport can repeat after lease expiry/old worker resume. Durable Notification.eventKey uniqueness/upsert is the business dedup. B07 checks claim death, retry after publish failure and one durable notification. Do not claim exactly-once delivery. Fix transport, wait/inspect lease, retry; do not erase events. Proposed role: backend notification operator.
- **Security outbox:** atomic claim with UUID leaseId, 30s lease; marker/retry use leaseId CAS; failed publish retries about5s later. B07 kills after actual publication before marker, expires lease in the fixture and observes repeated transport of the same event. DB family revocation remains durable. Proposed role: backend/security operations. Do not roll back to code ignoring revokedAt/sid.

Claim-expiry checks use actual DB predicates, with fixture leaseUntil advanced into the past after owned process death. The drill does not claim it waited every natural 30/60s lease. Scheduler drains are actual exported worker ticks executed by two disposable processes; timer cadence itself is also booted by the separate server entrypoint fixture. No provider/email/SMS/upload effects are introduced into transaction callbacks.

## Alerts and failure of alert delivery

Existing admin health-summary is observation only; it did not previously deliver alerts. New `scripts/dispatch-operations-alerts.js` is an explicit opt-in adapter. Caller supplies authenticated summary reader, sink delivery, persisted state save and scheduling. Import does not load dotenv, connect or send. It is not automatically wired into production startup by B07.

The actual local path is HTTP admin summary → dispatcher → HTTP sink; it emits only queue/status/count/observedAt, ignores arbitrary source fields, uses generation idempotency keys and persisted pending state, and coalesces repeats for60s by default. Immediate recovery transitions bypass repeated-firing suppression. Failed delivery keeps pending payload/key and deliveryFailed=true for retry. A scheduler must also surface source-reader exceptions and a dead-man heartbeat; a missing notification is not proof of health. The sink should dedup idempotency keys, since a lost response can cause delivery replay.

Proposals from existing summary: unresolved webhook/outbox older15min; pending refund older24h; user attempt count>=8000 warning and10000 admission cap. Refund age is a human workflow signal, not proof of financial fault. Capacity recovery must not delete durable references; route decisions need capacity/abuse review. Proposed ownership: platform/backend for queue health, finance operations for evidenced refund resolution, product/security owner for durable-attempt capacity policy. No person, channel or response-time SLO is assigned here. Local sink does not prove email/Slack/pager readiness. Encryption/authentication, deployment scheduling and retention of alert state need owner review before wiring a live sink.

## Backup and restore

The earlier runbook references PowerShell files absent from this checkout. The old `scripts/drill-backup-disposable.js` is historical and lacks the ownership/evidence controls of the B07 harness; do not use it unchanged on an existing resource.

B07 uses newly owned Docker Mongo with installed mongodump/mongorestore, tmpfs data, no shared volume. Quiesce all source child writers/worker ticks, seed the final marker, then dump the single database. Do not call this a consistent live-writer backup or PITR. Copy the fixture gzip archive out to ignored `artifacts/b01/<run>/b07-fixture.archive.gz`; retain checksum and tool/version metadata. Archive is synthetic fixture only, never commit it. Verify access restrictions before any real archive; local unencrypted retention is not an operational backup policy.

Restore the retained host file into a new exact namespace, without --drop; confirm the destination initially has no collections. Hash raw file bytes, not an EJSON/JSON representation of a Buffer. Copy that file into the owned container for restore and compare host/container SHA-256 immediately before and after the command. Retain all four hashes, the archive basename and the same run ID in evidence. A decompressed checksum helps investigation but does not prove which file was restored. Compare each collection's count/document fingerprint and all index options; normalize only the order of index-list entries by name, while retaining compound key order, unique/TTL/partial/sparse options. Check references, receipt partition and checkout allocation equations, pinned versions and session/tombstone policy. Start only a destination app fixture with no business workers; source app remains stopped. Verify read/replay, session auth and termination before calling local recovery usable.

Measure dump, restore-tool duration and end-to-end observed local RTO separately. B07 RTO starts immediately before mongorestore and ends after index/data/ledger validation plus destination HTTP replay/session/tombstone checks; it excludes outage detection, host provisioning, secrets/DNS, routing, production workers and third-party validation. RPO is acknowledged fixture writes lost against the quiesced marker (expected0); not a continuous-backup RPO. Encryption, rotation/retention, offsite copies, PITR, restored alert/provider routing and multi-node recovery remain unverified proposals. Proposed roles: database operator performs restore, backend validates invariants, finance owner reviews ledger before traffic resumes.

## Migration and CAS rollback

Inventory: B03 identity review (collision/manual index classification); merchant ownership; commerce-integrity owner/flag manifest; checkout reconstruction; payment-ledger v1 classification; box version-field metadata. Do not infer account merge, historic purchased contents or owner transfer from names/legacy flags. Dedicated B07 runs collision review plus commerce owner/flag manifest on a quiesced clone containing real fixture ledger/session/tombstone relations. Existing full-suite migration tests are reused regression, not independent live rollout evidence.

Dry-run first and fingerprint data/indexes. Conflicts now block commerce manifest apply/rollback before transaction; this B07 tooling correction is documented with its failing regression. Review exact database and every proposed preimage/postimage. Unsupported/stale manifests stop; a fresh rerun with no remaining changes is idempotent. A controlled exception after an earlier write demonstrates transaction rollback.

Rollback only via reviewed CAS manifest. If another writer changed any expected postimage, whole transaction refuses to clobber it. Investigate, then review an explicit safe subset if appropriate; do not bulk unset fields or overwrite the writer. Old manifest format represents absent owner/flag preimages as null: value-level rollback can restore null instead of physical absence. This retained contract is explicitly tested; it is not a byte-identical metadata round trip. If field presence affects a real dataset, require a new reviewed migration format before rollout. Financial documents, attempt references, pinned versions and session records must remain unchanged. No index drop/sync is needed by this owner/flag apply. B03 index-removal workflow requires a separate owner-reviewed decision; it is not invoked by the dedicated B07 drill.
