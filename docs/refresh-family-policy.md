# Refresh family policy

Design recorded before implementation. A family is one AuthSession (`sid`), not an account. Access JWT claims including name/email remain compatible. FE was inspected read-only: `src/app/middleware/axiosMiddleware.js` retries refresh with a 10s timeout and coalesces requests only within one runtime; `tokenMiddleware.js` exposes decoded claims. No FE changes.

## State machine

- ACTIVE(current hash, history, absolute expiry): current refresh rotates atomically in a MongoDB transaction to a deterministic HMAC-SHA384 successor, retaining only the consumed SHA256 hash, consumption time and retry counter. The HMAC domain includes sid and the presented token; JWT_REFRESH_SECRET must be stable across instances/restarts. Neither raw token nor encrypted token is stored/logged.
- ACTIVE + consumed hash: accept at most TWO duplicate requests strictly before 30 seconds after consumption, only if the derived successor is still current. Atomically increment the persisted counter and return that successor, without extending expiry or rotating again. No IP/user-agent binding: these are neither stable identifiers nor proof of possession. Binding is to the exact opaque credential, family, current successor and active user/tokenVersion.
- ACTIVE + known consumed hash outside those conditions: transition to REVOKED and insert security outbox in the same transaction. Return 401, clear cookies. This is suspected reuse, not proof of theft. An attacker holding the old credential can also recover within this window; legitimate late retries can revoke a family.
- ACTIVE + current hash when 4096 hashes have already been consumed: revoke and require login rather than evicting evidence. Maximum 4096 history entries per family; no unbounded array growth. This is an explicit rotation admission limit within the 30 day family lifetime.
- REVOKED or EXPIRED: reject refresh and access, regardless of TTL cleanup. Unknown/malformed hashes: reject without revoking unrelated families.

Two simultaneous requests serialize on the same session document: one rotates, the other uses one retry allowance and receives the same successor. A lost response after commit is recovered by presenting the old cookie within the policy. Timeout/restart uses the same durable history/counter and stable HMAC key; there is no in-memory recovery dependency. If the successor has already rotated when an old request is authenticated, that request revokes instead of returning a stale successor. An already accepted response can still arrive out of order and overwrite a browser cookie: HTTP Set-Cookie has no compare-and-swap. The next retry can recover only within the same bounded policy; otherwise reauthentication is required. No policy can reliably distinguish theft from retry solely from duplicate presentation.

## Storage, expiry and revocation

History lookup uses an indexed multikey hash field; current hash and sid retain unique indexes. History and revocation tombstones remain authentication evidence until the original absolute expiresAt (30 days from login); TTL removes the whole document asynchronously after expiry. Physical deletion can lag the deadline when TTL/Mongo is delayed or unavailable. There is no per-hash eviction before family expiry. At the cap, consumed-token retries can still use their existing bounded allowance; further current-token rotation revokes. Every authentication query/refresh explicitly checks expiry and revokedAt. Rotation never extends lifetime. Logout/password reset may delete families through existing transactional revocation; absence also denies access. No cleanup against production data is part of rollout.

Reuse revokes only that sid; other devices/families and account tokenVersion remain intact. New access requests read the DB and reject the revoked sid immediately after commit. Local family streams close after commit; Redis outbox signals other instances with sid. Missed signals are covered by DB validation on the 20s heartbeat (plus DB response latency; no hard bound during a stalled query). Redis outage closes streams through existing fail-closed health checks; DB revocation remains authoritative and outbox retries. Outage-wide stream closure can temporarily affect other families, but does not revoke their DB sessions.

## Session policy and transition

Production AND NODE_ENV=staging require sid consistently for HTTP auth, ticket consumption and SSE heartbeat. Secure cookies apply in both. Staging also uses production configuration validation, including Redis TLS, proxy and origins. No sid-less fallback in these environments. Local/test retains explicit legacy compatibility; tests must exercise strict staging policy separately.

Deploy updated code and indexes together across all instances before enabling staging/production traffic; mixed old/new refresh writers are unsupported. Existing opaque cookie sessions rotate into history on first use. Previously consumed pre-cutover refresh hashes cannot be reconstructed; unknown old credentials are rejected without inferring family ownership. Legacy sid-less access and legacy JWT refresh tokens require interactive login at cutover; retain name/email claims. Notify users of reauthentication; no migration is run automatically. Verify JWT_REFRESH_SECRET is identical on instances without exposing it. Changing it invalidates recovery; revoke sessions and require login during key rotation.

Rollback: stop refresh traffic, deploy a version that still enforces revokedAt and strict sid policy, invalidate affected sessions and require login before reopening. Do not roll back to an implementation that ignores durable tombstones; it would reactivate access JWTs. No FE rollout or staging deployment is authorized here.

API: POST /api/home/refresh keeps request/cookie and success response shape. Bounded duplicates now return 200; out-of-policy reuse returns 401 and revokes that family. Cookie write CSRF header remains X-TotMart-Request: 1. Local reverse proxy tests are fixture verification only, never evidence of real staging.
