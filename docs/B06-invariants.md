## Financial reconciliation equations

All amounts below are integer VND, not floating currency units. Scope is version-2 incoming receipts. Let `E` be sum of distinct PaymentEvent.transferAmount; `A` sum PaymentAllocation.amount; `U` sum unallocated event amounts; `Dpending`/`Dcompleted` direct unallocated-receipt refunds identified by event disposition refund_pending/refunded. Then:

`E = A + U + Dpending + Dcompleted`.

Each event has at most one allocation (unique eventId). Each checkout's `receivedAmount = sum(allocations for that checkout)`. An allocated event's whole amount is counted in A even when it exceeds principal; **do not add surplus to E or A again**. Direct receipt refunds are outside A. Audit records and display-only overpaidAmount are not additional money.

For allocated money, classify pending/completed ReceiptRefund amounts with purposes surplus, unpaid, order and subscription. For an open partially paid checkout, A remains held pending settlement. For a settled/cancelled checkout, `A = retained principal + pending allocated refunds + completed allocated refunds`; refunded principal is subtracted from retained principal. For a fully cancelled product purchase retained principal is zero. The multi-merchant test asserts 200009 allocated = 200002 principal refunds + 7 surplus, and a later 5000 direct receipt refund brings E to 205009 without changing A. Completing one principal refund moves it from pending to completed; pending plus completed stays 205009. Duplicate bank reference cannot complete another refund; audit count remains one.

The subscription test asserts `270012 allocated = 90002 retained delivered value + 180003 pending principal + 7 pending surplus`. It does not count the same refund again through Subscription.refundAmount. Partial receipt 60000 followed by expiry/cancel creates exactly one unpaid pending refund 60000, consumes no stock, and keeps the receipt/allocation/audit. Existing paymentReconciliation tests retain duplicate provider/reference, partial/overpaid/late receipt and worker-retry behavior.

Receipt identity admission uses an upsert with Mongoose timestamps before payload hash comparison. An invalid same-identity/different-amount webhook returns 409 and can update only that existing event's updatedAt; this is an **observed metadata exception**, not proof of zero DB writes. B06 compares every other event field and every other business collection unchanged and checks timestamp monotonicity. No runtime change was introduced to suppress this existing behavior. This exception does not permit attempts, amounts, allocation, refund, checkout or audit changes on payload conflict.

## Measured performance and limits

Representative route: GET manager/products with existing ownership scope, stable `{createdAt:-1,_id:-1}` and page/limit. Fixture assumptions are published in the benchmark artifact: 1200 products, 8 owners/brands, 150 products/brand, 120 visible for measured owner after archived/conflicting ownership exclusions, ownerless legacy rows included under own brand, identical createdAt to force tie cases. No writes during pagination. Concurrency 1 and 4, five warmups each, forty measured requests each, repeated unchanged-source control. Measure p50/p95/errors, Mongoose operation count, existing index catalog, actual executionStats and winning plan; assert six pages plus empty seventh exactly match all 120 IDs with no duplicate/missing row.

This is an assumed fixture, not confirmed production scale. Debug counts Mongoose operations, not every wire command, auth Redis command or transaction retry. The query benchmark runs one app process/real disposable mongod with Redis disabled; separate HTTP acceptance proves two processes/real Redis. Jest instrumentation/Windows/local cache/connection pool influence latency. No optimization or index was added: before/after is an unchanged-source repeat/control, not a speedup claim. No latency SLO, growing-dataset behavior, concurrent-write offset pagination guarantee or complete API query certification is inferred. Other older lists (including refund/template lists sorted only by createdAt) still need separate tie/order/explain review before claiming stable pagination across all APIs.
